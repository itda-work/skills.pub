결제 승인 API 장애 회고

2026년 8월 19일 14시 07분부터 14시 49분까지 42분간 페이루프 결제 승인 API 의 오류율이 최대 35.4% 까지 상승해 승인 요청 98,861건이 실패했다. 원인은 배포 v4.18.0 에 포함된 데이터베이스 커넥션 풀 설정의 환경변수 이름 오타로, 풀 상한이 200에서 기본값 40으로 축소되면서 피크 트래픽에 풀이 고갈된 것이다. 롤백으로 복구했고 데이터 손실은 없다.

오류 추이 지표#

5분 집계 버킷 기준 오류율과 실패 유형 구성이다. 원본 13개 버킷의 요청·실패 건수는 부록 A 에 전량 수록했다.

결정

실패 유형 분류는 애플리케이션 예외 코드가 아니라 db.pool.acquire.timeout 스팬 유무를 1차 기준으로 삼았다. 예외 코드만으로 세면 커넥션 타임아웃이 업스트림 5xx 로 위장돼 원인 비중이 절반 이하로 보인다.

근본 원인#

v4.18.0 에 포함된 커넥션 풀 설정 리팩터에서 환경변수 이름의 밑줄 하나가 빠졌다. 오버라이드가 적용되지 않아 라이브러리 기본값 40이 쓰였고, 피크 트래픽의 동시 요청 수가 그 값을 넘어서면서 획득 대기가 250ms 타임아웃을 초과했다.

diff 
# payloop-auth/config/db.yaml — v4.17.3 → v4.18.0
 pool:
-  maxSize: ${AUTH_DB_POOL_MAX:-200}
+  maxSize: ${AUTH_DB_POOLMAX:-40}
   acquireTimeoutMs: 250
   idleTimeoutMs: 30000
   validationQuery: "SELECT 1"

배포 환경에는 AUTH_DB_POOL_MAX=200 이 설정돼 있었으나 새 이름 AUTH_DB_POOLMAX 는 정의된 적이 없다. 설정 로더는 미정의 변수를 오류로 다루지 않고 기본값으로 조용히 대체한다. 부팅 로그에도 경고가 남지 않았다.

평시 동시 요청 수는 노드당 60~90 수준이라 상한 40으로는 처음부터 부족했다. 14:02 배포 직후 5분간은 순차 배포로 구버전 노드가 트래픽을 나눠 받아 증상이 가려졌고, 14:06 마지막 노드가 교체되면서 전면화됐다.

위험

같은 설정 로더를 쓰는 서비스가 정산(payloop-settle)·정기결제(payloop-recur) 등 11개 더 있다. 미정의 환경변수의 조용한 기본값 대체는 이 11개 전부에서 동일하게 성립하므로, 액션 A-1 은 결제 승인 서비스 한정이 아니라 공용 로더 계층에서 처리한다.

핫픽스 전진 배포 대신 롤백을 택했다. 원인이 설정값 한 줄이라 핫픽스가 더 빠를 수 있었지만, 확정 시점(14:36)에 이미 29분이 경과해 검증되지 않은 배포를 추가로 넣는 위험을 피했다.

잘된 점과 아쉬운 점#

개인의 판단 착오가 아니라 관측 배치와 게이트 설계의 문제로 본다. 같은 상황에서 다른 온콜이 대응했어도 원인 규명 소요는 비슷했을 것이다.

잘된 점#

  • 알림 임계가 적절해 오류율 18.6% 시점에 4분 만에 감지됐다. 임계를 5%로 잡은 것이 유효했다.
  • 결제수단별 실패율 차이를 단서로 삼아 업스트림 가설을 기각한 판단(14:23)이 규명의 전환점이었다.
  • 핫픽스 대신 롤백을 택한 결정이 추가 위험을 만들지 않았다. 검증된 아티팩트로 되돌리는 것이 29분 경과 시점의 옳은 선택이었다.
  • 멱등키 설계 덕분에 재처리에서 이중 승인이 0건이었다.

아쉬운 점#

  • 커넥션 풀 사용률에 알림이 없었다. 지표는 수집되고 있었지만 아무도 보지 않는 대시보드 3번째 탭에 있었다 — 수집과 관측은 다르다.
  • 배포 후 자동 검증이 헬스체크뿐이었다. 오류율 기반 카나리 게이트가 있었다면 14:04에 자동 차단됐다.
  • upstream_5xx_ratio 알림이 2차 효과를 1차 원인처럼 보이게 했다. 파생 알림에 인과 방향 표시가 없다.
  • 설정 변경이 코드 리뷰를 통과했다. 환경변수 이름 변경은 diff 상 한 글자라 사람이 잡기 어렵다.
주의

「리뷰를 더 꼼꼼히 한다」를 액션으로 넣지 않았다. 이 결함은 사람의 주의력으로 막는 종류가 아니다 — 정의되지 않은 환경변수를 부팅 시점에 실패로 만드는 것이 유일하게 재현 가능한 방어다.
